# Метаслой FAS: дорожная карта

Поэтапная доставка целевой модели из [meta-layer.md](meta-layer.md). Каждый этап **отдельно поставляем**: сначала документы и контракты, затем код. Порядок фаз 1–2 пользователь может поменять (provenance ↔ `SemanticModelVersion`); ниже — рекомендуемый старт.

Связь с задачами трекера: целевая модель — FAS-3; эта дорожная карта — FAS-4. Дальнейшая нарезка на фазовые задачи — после принятия документов.

## Принципы нарезки

1. **docs → contracts → code** внутри каждой фазы.  
2. Фаза не ломает читателей текущих Parquet и API без MAJOR `fas_schema_version`.  
3. Нет Iceberg/Hive writers ни в одной фазе.  
4. FAS остаётся одним приложением.  
5. Не дублировать `fact_observation` + `bindings` новой «широкой» таблицей фактов.

## Обзор фаз

| Фаза | Название | Закрывает | Поставка |
|---|---|---|---|
| 0 | Документы целевой модели | — | этот PR |
| 1 | Контракт провенанса финансового факта | G3 | docs + контракт + тонкий код/тесты |
| 2 | Публичный `SemanticModelVersion` | G4 | docs + манифест + поля API/`run` |
| 3 | Financial Model Catalog | G1 | каталог показателей + версия в SMV |
| 4 | Три графа и трассировка | G2 | контракт рёбер + проверки join |
| 5 | Внешний контракт DataMesh | G5 | published promises + инвариантные тесты |

## Фаза 1 — Provenance contract финансового факта (рекомендуемый первый инкремент кода)

**Зачем первой:** даёт язык для аудита и Mesh без перестройки каталогов; опирается на уже существующие колонки.

**Docs:** спецификация логической записи `FinancialFactProvenance` (имя уточняемо): обязательные поля, источники (join-ключи), что запрещено копировать.

**Contracts:** JSON Schema или раздел design; пример сборки из `fact_observation ⨝ dim_row ⨝ bindings ⨝ dim_period` (+ опционально `row_semantics`).

**Code (тонкий):** чистая функция/представление сборки; контрактные тесты на golden-книге; без новой широкой таблицы чисел. Допустимы nullable колонки-ссылки только если без них join нестабилен (additive MINOR) — предпочтение отдать документации join.

**Не-цели фазы:** новый датасет с дублированием `value*`/`concept`; UI; Iceberg; изменение конвейера привязки.

**Поставка:** [financial-fact-provenance.md](financial-fact-provenance.md); код `finance_analysis.domain.provenance`; тесты `tests/unit/test_financial_fact_provenance.py`.

**Критерии приёмки:**

- [x] Документ контракта в `docs/` (или § design) с полями и правилом «без дубля факта».  
- [x] Тест: для строки golden-фикстуры собирается полный провенанс (concept, period, cell, binding source/version, build_key, derive_key / SMV stub).  
- [x] Явно перечислено, какие поля берутся из какого датасета §4.4.

## Фаза 2 — `SemanticModelVersion`

**Зачем:** один публичный id вместо россыпи версий в ответах и `run`.

**Docs:** состав агрегата (taxonomy, glossary, metrics, model_types, units/dimensions, rules, schema); отличие от `derive_key`; правила bump (когда новый id).

**Contracts:** формат манифеста в object store (например `semantic_models/{version}.json` + указатель); поле в `_head.versions` / `AnalysisResult.versions` / `run`.

**Code:** вычисление версии из канонического набора артефактов; запись при релизе глоссария / смене пакета; чтение в API. `derive_key` не удаляется и не переименовывается.

**Не-цели фазы:** OSI/Ossie export; объединение `derive_key` и SMV в один хеш; перенос метрик в object store, если достаточно git-отпечатка в составе SMV.

**Критерии приёмки:**

- [ ] Манифест `SemanticModelVersion` воспроизводим (одинаковые входы → одинаковый id).  
- [ ] Ответ с данными книги и `run.parquet` содержат id рядом с `derive_key`.  
- [ ] Документирована матрица: какой артефакт входит в SMV vs только в `derive_key` (журнал, embed-модели и т.д.).

*Пользователь может поставить фазу 2 перед фазой 1; критерии от этого не меняются.*

## Фаза 3 — Financial Model Catalog

**Зачем:** закрыть G1 — показатель как сущность, а не только YAML для кода.

**Docs:** модель показателя (id, определение, входы, единицы, окно, варианты по `model_types`, статус).

**Contracts:** схема каталога; включение отпечатка/версии каталога в `SemanticModelVersion`.

**Code:** загрузка/валидация каталога (поверх `configs/metrics` + связи с таксономией); отказ от «тихих» расхождений concept vs metric inputs; API чтения каталога (опционально в той же фазе или сразу после).

**Не-цели фазы:** переписывание всех правил аудита; автоматический вывод формул из `composed_of`; отдельный сервис метрик.

**Критерии приёмки:**

- [ ] Каждый публичный metric id имеет запись каталога с входами-понятиями и единицами.  
- [ ] CI/тест: входы метрик ⊆ понятия таксономии (с явному исключением вроде `row_fallbacks`, решение 40).  
- [ ] Версия каталога входит в `SemanticModelVersion`.

## Фаза 4 — Три графа и трассировка

**Зачем:** G2 — Excel / семантика / формулы метрик с прослеживаемостью.

**Docs:** три графа, типы узлов/рёбер, запрет схлопывания, путь трассировки «метрика → факт → ячейка».

**Contracts:** стабильные идентификаторы рёбер; как `graph_links` соотносится с семантическим ребром и с ребром метрики.

**Code:** проверки целостности (каждый вход метрики с основной привязкой имеет физический след либо явную причину отсутствия); представления/API трассировки (read-only). Без графовой БД.

**Не-цели фазы:** замена networkx-эвристик привязки; полный lineage UI; запись третьего графа как копии YAML в Parquet без нужды.

**Критерии приёмки:**

- [ ] Документ трёх графов + примеры на одной книге.  
- [ ] Тест трассировки: выбранный metric → concept → binding_key → cell_id (или явный `missing_trace`).  
- [ ] Нет миграции, смешивающей три графа в одну таблицу рёбер с общей семантикой.

## Фаза 5 — Внешний контракт DataMesh

**Зачем:** G5 — обещания читателю озера без писателей каталога таблиц.

**Docs:** «Published Parquet contract»: датасеты, ключи, типы, семантика полей, маркеры, история, эволюция схем, что FAS не гарантирует (list-before-marker, cross-bucket transactions, Iceberg).

**Contracts:** версия контракта; совместимость с §4.11–4.12; опционально machine-readable index наборов.

**Code:** контрактные тесты «зафиксированная сборка читается только по маркеру»; совместимость `schemas/*.json` с опубликованной таблицей полей; без Hive Metastore / PyIceberg.

**Не-цели фазы:** `LakePublisherPort`, внешние таблицы, Airflow-операторы внутри FAS, `_consumers` (снято в design).

**Критерии приёмки:**

- [ ] Документ контракта сослан из meta-layer и design.  
- [ ] Тесты маркеров и аддитивной эволюции зелёные.  
- [ ] В коде нет зависимости на Iceberg/Hive writers.

## Зависимости между фазами

```text
0 docs
 └── 1 provenance ──┐
 └── 2 SMV ─────────┼──► 3 Financial Model Catalog ──► 4 three graphs
                    │
                    └──► 5 DataMesh contract (может начаться после 1–2 параллельно с 3–4)
```

Фазы 1 и 2 независимы друг от друга. Фаза 3 предпочитает 2 (чтобы версия каталога сразу жила в SMV). Фаза 4 предпочитает 1 и 3 (трассировка факта и показателя). Фаза 5 может идти параллельно после 1–2.

## Вне рамок всей дорожной карты

- Отдельные микросервисы или отдельные БД под метаслой.  
- Iceberg / Hive / Delta writers и Metastore.  
- Возврат OSI semantic-model export.  
- Удаление истории сборок или `derived/` ради Mesh.  
- Схлопывание трёх графов в один store.
