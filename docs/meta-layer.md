# Метаслой FAS: целевая модель

Документ фиксирует **целевую** модель метаслоя. Реализация — по [метаслой: дорожная карта](meta-layer-roadmap.md). Нормативное поведение текущего кода — [design-v0.23.md](design-v0.23.md) (§4, §5). Если этот документ и код расходятся, сервис делает то, что в коде, пока соответствующая фаза дорожной карты не принята.

FAS остаётся **одним приложением** с ясными доменными границами. Отдельные сервисы и отдельные БД целевая модель не требует.

## 1. Два смысла «метаслоя»

| | Семантический метаслой | Технический метаслой |
|---|---|---|
| Вопрос | Что означает число и как оно связано с понятиями, метриками и правилами | Как снимок записан, версионирован и обнаружен |
| Содержание | Таксономия, глоссарий, привязки, семантика строк/периодов, формулы метрик, типы моделей, единицы, правила | Раскладка ключей, схемы Parquet, `fas_schema_version`, маркеры фиксации, `build_key` / `state_seq` / `derive_key`, указатели `_head` |
| Потребитель | Аналитик, правила аудита, Wren/MDL, обучение глоссария | Wren `read_parquet`, загрузчик, GC, внешний DataMesh (позже) |

Семантика без технического контракта не воспроизводима. Технический контракт без семантики — это просто файлы. Целевая модель держит оба слоя явно и не смешивает их в одну таблицу «всего обо всём».

## 2. Что уже есть (база §4.4 и соседние разделы)

Звезда Parquet книги и производное состояние уже закрывают технический каркас и часть семантики.

### 2.1 Проекция builder (неизменяемая на `build_key`)

| Датасет | Роль |
|---|---|
| `dim_row` | Строки: `row_key`, стабильный `binding_key`, лист, путь подписи, единица/валюта/масштаб, формула |
| `dim_period` | Периоды осей: зерно, ключи, маркеры, флаги, даты, `timeline_id` / `axis_kind` |
| `fact_observation` | Ячейки: `cell_id`, сырое и DECIMAL-значение, статус |
| `graph_links` | Развёрнутые ссылки формул Excel (`cell` → `ref_cell`, класс формулы) |

Схемы — `src/finance_analysis/adapters/storage/schemas/*.json`, версия в `manifest.json` → `fas_schema_version`. Правила записи — design §4.12.

### 2.2 Производное состояние (`derived/{derive_key}/`)

| Датасет | Роль |
|---|---|
| `bindings` | Привязка fact-строки к понятию: `concept` / `status` / `source` / `confidence`, `evidence_json`, `matched_label_id`, версии глоссария и таксономии, `decided_by`, `stale` |
| `row_semantics` / `period_semantics` | Знак, природа, агрегация, фаза периода, evidence |
| `coverage` / `questions` | Покрытие и пакет вопросов книги |

`derive_key` — хеш входов свёртки (в т.ч. `state_seq`, `glossary_version`, `taxonomy_version`, калибратор, модели, профиль, `fas_derive_version` из `PACKAGE_SOURCES`/`CONFIG_SOURCES`, типы моделей, роли листа). Это **внутренний** ключ воспроизводимости папки `derived/`, не публичный контракт семантической модели для внешних систем.

### 2.3 Каталоги определений (git + object store)

- Таксономия понятий — `configs/concepts/`, связи на понятии (`composed_of`, `related_to`, …); расчёт из связей не выводится (design §5.1).
- Глоссарий меток — `configs/glossary/`, релизы в `glossary/releases/{version}/`, голова `glossary/_head.json`.
- Метрики — `configs/metrics/` (числитель/знаменатель, окна, варианты).
- Типы моделей и роли листов — `configs/model_types/`, `configs/sheet_roles.yaml`.
- Результаты прогона — `run` / `ratios` / `findings` с закреплёнными версиями.

### 2.4 Уже есть провенанс — но фрагментарный

На уровне привязки и метки глоссария уже видны происхождение и версия (`bindings.source`, `evidence_json`, `matched_label_id`, `glossary_version`, provenance метки в релизе). На уровне ячейки есть `cell_id` и значения. **Единого контракта «финансовый факт»** (понятие × период × значение × происхождение × версии модели), который не дублирует `fact_observation`+`bindings`, ещё нет — это gap ниже.

## 3. Пять разрывов относительно цели

### G1. Полная модель финансового показателя

Сейчас: понятия в таксономии, формулы в `configs/metrics`, варианты и `row_fallbacks` рядом, без единого каталога «показатель = определение + входы + единицы + применимость к типу модели + статус качества».

Цель: **Financial Model Catalog** — явная сущность показателя (идентификатор, определение, формула/входы, единицы, окно, варианты по типу модели, ссылки на понятия, версия). Связи таксономии по-прежнему не считают; формулы живут в каталоге метрик, но читаются как часть одной версионируемой модели.

Спецификация фазы 3: [financial-model-catalog.md](financial-model-catalog.md).

### G2. Три графа с прослеживаемостью, без схлопывания

Нужны **три** графа, связанные ссылками, а не одна смешанная сеть:

| Граф | Узлы / рёбра | Сейчас |
|---|---|---|
| Физический Excel | Ячейки, формулы, `graph_links` | Частично (`graph_links`, поля формулы в `dim_row`) |
| Семантический | Понятия, привязки строк, иерархия/`composed_of` | Частично (таксономия + `bindings`) |
| Формульный метрик | Показатель → входы-понятия (и варианты) | В YAML метрик, без явного графового контракта и без стабильной трассировки к физическим ячейкам |

Трассировка: показатель → понятия → `binding_key`/`row_key` → `cell_id` / ребро `graph_links`. Схлопывать три графа в одну таблицу нельзя: разные жизненные циклы и разные потребители.

Спецификация фазы 4: [meta-layer-graphs.md](meta-layer-graphs.md).

### G3. Контракт провенанса финансового факта

Нужен контракт (логическая запись или стабильный join-ключ), отвечающий: *какое понятие, в каком периоде, какое значение, из какой ячейки/строки, с какой привязкой и уверенностью, на каких версиях семантической модели и сборки*.

Он **не** копирует колонки `fact_observation` и `bindings` в третью широкую таблицу «на всякий случай». Он задаёт обязательные поля и правила сборки поверх существующих датасетов (и при необходимости тонкий индекс/представление). Дублирование факта запрещено.

Спецификация фазы 1: [financial-fact-provenance.md](financial-fact-provenance.md).

### G4. Публичный `SemanticModelVersion`

Сейчас версии размазаны: `glossary_version`, `taxonomy_version`, отпечатки метрик/правил/типов в `run` и в формуле `derive_key`, `fas_schema_version` в манифесте.

Цель: один публичный идентификатор **`SemanticModelVersion`**, агрегирующий согласованный набор:

- taxonomy  
- glossary  
- metrics  
- model types  
- units / dimensions  
- rules (аудит)  
- schema (`fas_schema_version` / имена датасетов)

`derive_key` остаётся внутренним ключом свёртки книги (входы включают журнал и модели эмбеддинга). `SemanticModelVersion` — контракт «какая семантика действовала», рядом с `derive_key`, без подмены одного другим. Публикация — документ/манифест в object store + поле в ответах API и в `run`.

Спецификация фазы 2: [semantic-model-version.md](semantic-model-version.md).

### G5. Внешний контракт для DataMesh

FAS **публикует обычный Parquet** в своей раскладке. FAS **не** создаёт таблицы Iceberg/Hive и не обещает SLA оркестраторам (design §4.11).

Для Mesh нужны зафиксированные обещания поверх того, что уже почти есть во внутренних правилах §4.11–4.12:

- стабильные имена датасетов, колонок, типов и семантика полей (`schemas/*.json`);  
- стабильные идентификаторы (`model_id`/`job_id`, `build_key`, `binding_key`, `concept`, версии);  
- маркеры фиксации (`manifest.json`, `_done.json`, `result.json`, `glossary.json`) как сигнал «можно читать»;  
- история сборок и релизов без тихого удаления (§4.10);  
- аддитивная эволюция в пределах MAJOR.

Внешний контракт — документ + тестовые инварианты; писатели озера в чужом каталоге — вне рамок FAS.

## 4. Целевая концептуальная структура

Шесть доменов внутри одного приложения и одного object store. Границы — логические (пакеты/префиксы/API), не микросервисы.

```text
┌─────────────────────────────────────────────────────────────┐
│                    Versioned Metadata Contract              │
│   SemanticModelVersion · fas_schema_version · publish marks │
└─────────────┬───────────────────────────────┬───────────────┘
              │                               │
   ┌──────────▼──────────┐         ┌──────────▼──────────┐
   │  Semantic Catalog   │         │ Financial Model     │
   │  taxonomy+glossary  │◄───────►│ Catalog (metrics,   │
   │  units, dimensions  │         │  variants, rules)   │
   └──────────┬──────────┘         └──────────┬──────────┘
              │                               │
              │         Semantic Bindings     │
              └──────────────┬────────────────┘
                             │
              ┌──────────────▼──────────────┐
              │      Book Metadata          │
              │  dim_* · facts · graph_links│
              │  build_key · journal        │
              └──────────────┬──────────────┘
                             │
              ┌──────────────▼──────────────┐
              │   Analytical Metadata       │
              │  coverage · questions ·     │
              │  findings · ratios · run    │
              └─────────────────────────────┘
```

| Домен | Содержимое | Уже / цель |
|---|---|---|
| **Semantic Catalog** | Понятия, метки, единицы, измерения, иерархия | Есть (git + релизы); цель — явная публикация как части `SemanticModelVersion` |
| **Financial Model Catalog** | Показатели, формулы, варианты, применимость к `model_types`, правила аудита как версионируемый набор | [каталог фазы 3](financial-model-catalog.md); версия в SMV |
| **Book Metadata** | Проекция книги, физический граф, журнал решений | Есть §4.2–4.5 |
| **Semantic Bindings** | `bindings`, семантика строк/периодов, статусы unknown/ambiguous | Есть; цель — трассировка к трём графам (G2) и факту (G3) |
| **Analytical Metadata** | Покрытие, вопросы, findings, ratios, run | Есть |
| **Versioned Metadata Contract** | `SemanticModelVersion`, схемы, маркеры, история, обещания Mesh | Частично техника; цель — G4+G5 |

### 4.1 Инварианты границ

1. Один процесс FAS, один `ObjectStorePort`, Redis как и сейчас.  
2. Определения (каталоги) отделены от фактов книги; факты ссылаются на версии определений, а не копируют определения.  
3. Три графа (G2) связываются идентификаторами, не денормализуются друг в друга.  
4. Провенанс факта (G3) — контракт поверх join, не вторая копия чисел.  
5. Внешний Mesh читает Parquet и маркеры; Iceberg/Hive writers не появляются в FAS.

## 5. Связь с текущими ключами

| Ключ | Слой | Назначение |
|---|---|---|
| `build_key` | Book Metadata | Неизменяемый снимок проекции builder |
| `state_seq` | Book Metadata | Позиция журнала решений |
| `derive_key` | Bindings / Analytical | Внутренняя папка свёртки inferred⊕журнал |
| `glossary_version` / `taxonomy_version` | Semantic Catalog | Релизы определений |
| `fas_schema_version` | Versioned Metadata Contract | Версия схем Parquet |
| `SemanticModelVersion` | Versioned Metadata Contract | Публичный согласованный набор семантики ([спека](semantic-model-version.md)) |
| `binding_key` | Bindings | Стабильная привязка строки через пересборки |
| `concept` | Semantic Catalog | Идентификатор понятия |

## 6. Не-цели этого документа

- Код, миграции схем, новые HTTP-маршруты.  
- Писатели Iceberg/Hive/Delta.  
- Отдельная графовая СУБД.  
- Возврат снятого `GET /v1/semantic-model` в формате OSI (решение 31); публичный контракт версий — свой, не Apache Ossie.

Порядок закрытия разрывов — [meta-layer-roadmap.md](meta-layer-roadmap.md).
